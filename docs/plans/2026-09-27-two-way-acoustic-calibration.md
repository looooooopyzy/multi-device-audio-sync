# 双向声学校准与播放中网络自适应

## 目标与边界

在现有 Windows Master + iPad Safari 浏览器节点上，用两端麦克风测出 Windows 与 iPad 扬声器的相对发声延迟。校准以主控的测试提示音和 `tone` 串流为验收对象。系统 Loopback 模式中的 Windows 原应用直出声音仍有独立路由问题，不能把该模式的原声与 iPad 声音视为已经校准。

播放期间继续利用已有的时钟同步模型跟踪时钟漂移，并根据持续的网络延迟变化调整**所有节点共同使用**的呈现缓冲。网络包到达时间不用于改写声学校准值；声学校准值只由麦克风录音更新。

## 方案选择

| 方案 | 优点 | 限制 |
| --- | --- | --- |
| 一个放在聆听位置的 Windows 麦克风 | 实现和部署最简单，直接校准该位置的到达时间 | 不使用用户指定的 iPad 麦克风；结果只对该位置有效 |
| iPad 与 Windows 麦克风各录到两个扬声器的校准声 | 符合双向测量要求；每条录音内部相减可消去该麦克风的固定输入延迟 | iPad Safari 录音需要可信 HTTPS；双端录音受房间反射、回声消除和扬声器位置影响 |
| iOS 原生应用录音 | 不需要浏览器证书 | 重新引入原生构建和签名流程 |

采用第二个方案。先在一次连续录音中播放两次可识别的短扫频：Windows 扬声器在 `T` 播放，iPad 在 `T + G` 播放。iPad 麦克风和 Windows 麦克风都要录到**两次**扫频。单独用 iPad 录 Windows、再单独用 Windows 录 iPad，无法消去两端不同的麦克风输入延迟。

每端用模板匹配找到两次声响的样本位置，计算 `δ端 = (录到 iPad 声音的时间 - 录到 Windows 声音的时间) - G`。这一步只使用同一段录音里的样本差，因此不依赖两端麦克风的绝对录音时间。两个麦克风都靠近各自扬声器、互相传播路径近似对称时，`(δWindows + δiPad) / 2` 估计两端当前输出延迟的差。界面同时显示两端测量值与置信度；相关峰太弱、两端结果严重不一致或麦克风权限失败时，保留原校准值。

为避免让较慢设备在 200 ms 的实时缓冲中被迫提前播放，优先给较快设备增加非负延迟。浏览器现有 `calibrationMs` 继续作用于提示音和 PCM；Windows 本机提示音与 `tone` 输出增加同类延迟设置。改变实时 PCM 的全局呈现缓冲必须在串流边界重置时间线，让所有节点同步切换。

## 数据流与隐私

1. 用户在 iPad 点击“自动校准”，授予麦克风权限。Windows 主控检查默认录音设备。
2. 主控为本次测量分配会话 ID，安排两次扫频，并要求两端在同一个测量窗口持续录音。
3. 两端在本地分析录音，只交换两次峰值之间的时间差、峰值质量和会话 ID；麦克风原始音频不通过 WebSocket 发送或持久化。
4. 主控检查两端结果，计算并下发校准值；浏览器保存在现有本地设置中。
5. 时钟同步持续运行。浏览器上报音频包的到达余量与丢包，主控在网络持续恶化时为**全部**节点提升共同呈现延迟并重开串流；恢复时缓慢评估，避免反复跳变。

当前页面以局域网 HTTP 提供。iPad Safari 的麦克风 API 需要安全上下文，因此提供本地 HTTPS 入口和可安装的根证书；证书私钥留在 Windows。证书安装和信任须由用户在 iPad 上操作。浏览器拒绝录音或证书未受信任时，现有手动校准和音频播放仍可使用。

## 验收

- 合成录音中给两次扫频设置已知延迟与噪声，模板匹配能恢复差值，并拒绝过弱信号。
- 没有麦克风、权限拒绝、网络断开或测量超时时，不写入错误校准值。
- 两端测量完成后，Windows 与 iPad 的提示音以及 `tone` 音频应用新延迟；重复测量的结果稳定。
- iPad Safari 真机验证 HTTPS、麦克风权限、播放与录音并行、两端峰值和重新播放后的声学残差。未经真机录音，不宣称毫秒级声学精度。
- 网络抖动增大时能显示缓冲调整与迟到统计，所有扬声器仍使用同一主控时间线。
